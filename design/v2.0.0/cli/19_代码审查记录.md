## 2. 逐项审查结果

### 2.1 目录结构(§6.1)

- cli/ 自包含,不嵌套 pmem;新源文件位于 cli/src/interface/,符合三层结构。通过。

### 2.2 层级与无交互(§6.2)

- script 模块纯标准库,不触碰静态库;cmd_debug_run 只经公共 API 调库。
- 无 getchar/scanf/cin;`debug run` 执行完立即退出,会话状态全部在本次调用内存中。
- 一次调用 = 一次调试会话:attach → debug_attach → 逐条执行 → 清理 → debug_detach,
  无跨调用状态。通过。

### 2.3 API 使用(§6.3)

- 每个步骤调用的均为 deeptrace.h 真实公共 API(见 16_接口调用设计 逐条映射),
  无假调用、无 mock、无重复实现、无平台 API/第三方库。
- 能力完整性:脚本 op 表(21 个 op)与 14_参数列表、16_接口调用设计一致;
  未知 op/未知字段/非法值均有明确校验错误。通过。

### 2.4 模块职责(§6.4)

- main 只做调度;parser 构造请求;cmd_debug 分派 run 到 cmd_debug_run;
  cmd_debug_run 执行会话流程;printer 只做格式化。通过。

### 2.5 代码质量(§6.5)

- 退出码:脚本文件/JSON/校验错误 → 2;attach/debug_attach/步骤失败 → 1;
  continue 进程退出 → 报告并退出 1;正常 → 0。与 15_异常设计一致。
- 清理:成功/失败路径统一走 `cleanup_session`(唯一调用点),先清本次设置的
  guard → HW → SW,再 debug_detach;清理失败打印 warning 不改退出码。
- 错误格式 `Error: step N (op): <msg>`、JSON 错误带行列号;输出纯 ASCII。通过。

## 3. 审查发现与修复

| # | 级别 | 问题 | 修复 |
|---|------|------|------|
| 1 | 严重 | `write` op 接受空格分隔 hex(校验通过),但 `internal::hex_bytes` 不剥空格,
  `"DE AD BE EF"` 会被解码成错误字节 | cmd_debug_run.cpp write 分支先压缩空白再
  hex 解码(已修复) |
| 2 | 轻微 | `read` size 无上限,极大值会触发 bad_alloc(与既有 `mem read` 行为一致) | 与既有行为一致,暂不改动,记录在案 |
| 3 | 测试基础设施 | printer_test `capture()` 未在 fd 重定向前 flush,首个 capture 测试
  会混入 gtest "Running main()" 缓冲导致偶发失败 | capture() 在 _dup2 前加
  `std::fflush(stdout)`(已修复) |

## 4. 结论

修复后重新编译并全量运行单元测试:101/101 通过(连续 4 次稳定)。审查通过。
