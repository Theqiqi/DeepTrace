# deeptrace - 接口设计(修改模式)

> 引用:v1.2.0/deeptrace/10_接口设计.md。本版本新增接口细节:

## 1. debug_continue

- 前置:`attach(pid)` + `debug_attach()` 完成;`timeout_ms > 0`。
- 流程:
  1. `DebugWaitEvent(pid, timeout_ms, sw_addrs, out)`:先处理挂起的初始事件
     (继续直到 CREATE_PROCESS 被继续,使目标运行;若无挂起事件则短超时跳过),
     再在超时预算内等待调试事件:
     - EXCEPTION_DEBUG_EVENT → 填充 hit/exception/address/tid/rip(读线程
       上下文),**不继续该事件**(目标冻结),返回;
     - EXCEPTION_BREAKPOINT 且地址不在 sw_addrs(挂起断点列表)中:
       该异常是附加时系统断点(DbgUiRemoteBreakin,ntdll 内永久 int3),
       DBG_CONTINUE 跳过后继续等待,直到命中真实断点;
     - EXIT_PROCESS_DEBUG_EVENT → exited/exit_code,返回;
     - 其余事件 → ContinueDebugEvent(DBG_CONTINUE) 继续等待;
     - WaitForDebugEvent 超时 → 返回 Timeout(上层转 timeout 报告)。
  2. 若 hit 且异常码为 EXCEPTION_BREAKPOINT 且 address 在持久化软件断点记录中:
     `DebugConsumeBreakpoint(pid, tid, address, orig, &rip)`,填充 out.rip 后返回。
  3. 其余情况直接返回 out。

## 4. debug_detach 事件排空

- 目标可能停在挂起异常上(如断点命中后重新武装、又被立即命中)。直接
  DebugActiveProcessStop 会把挂起异常当作未处理异常,导致目标崩溃。
- detach 前先排空挂起事件:
  - EXCEPTION_BREAKPOINT:判断是否为我们的软件断点(地址在断点记录中,或
    该地址字节已非 0xCC 说明是已清除断点的残留异常);是则恢复原字节(如
    仍需)并把命中线程 RIP 倒回断点地址后 DBG_CONTINUE,让原始指令重新执行;
    系统断点(字节仍为 0xCC 的 ntdll int3)RIP 已在其后,直接继续不循环。
  - 其余事件直接 DBG_CONTINUE;
  - 连续 200ms 无新事件即视为排空完成。

## 2. DebugConsumeBreakpoint

- 前置:断点异常事件挂起(线程冻结于 address,RIP=address)。
- 流程:写回原字节 → 线程设 TF → ContinueDebugEvent(DBG_CONTINUE) → 等待该线程
  EXCEPTION_SINGLE_STEP → 读执行后 RIP → 写回 0xCC 重新武装 → 继续事件 → 返回。

## 3. 异常与错误

- NotAttached / InvalidArg / Timeout / Error;ContinueInfo 缺省全零。
