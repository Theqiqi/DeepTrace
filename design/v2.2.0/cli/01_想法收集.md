# deeptrace_cli - 想法收集(修改/添加功能,v2.2.0)

> 输入:对软件的不成形想法(添加功能)。本步骤只整理想法、梳理现状、判断类型,
> 不做设计决策(设计决策在需求分析/设计阶段完成)。版本号在 0.5 步确定为 v2.2.0。

## 1. 想法整理(用户口述,归纳)

**一句话需求**:传入汇编代码,在目标进程中执行。

**用户设想的完整流程**(分阶段):

```text
汇编文件(.asm/.s)
    │  ① 转裸机 .bin 文件(shellcode)
    ▼
.bin 文件 ──② 读取 shellcode → 分配地址 → 写入 → 输出分配首地址
    │
    ▼
③ 执行远程线程,触发一次
    │
    ▼
④ 复用远程线程触发 或 清除分配的地址
```

**用户提出的开放疑问**:

1. 是否支持「传入 .asm 后在内存中直接转 shellcode」,而不必经 .bin 文件?
2. 是否添加「16 进制字节 → .bin 文件」的写出功能?
3. 命令形态不确定:拆分为多个命令在 CLI 中组合?还是拆成几个可直接用于 CLI 的参数?
   还是打包为一个参数?
4. 不确定设想的流程本身是否正确。

## 2. 类型判定

- **修改/添加功能**(非新建程序)。理由:对既有 deeptrace_cli 添加能力,
  不改变程序形态(命令行无交互,一次调用一个操作)。
- 涉及既有命令组:**asm**(汇编)、**shellcode**(注入)、可能 **convert**(16 进制写出)、
  **thread**(远程线程)仅作参照。
- 后续按 `.flow/cli_无交互_新建与修改程序流程.md` 修改模式执行受影响步骤,
  每个分析文档标注「改动点」。

## 3. 现状梳理(只读现状,本步不改动任何代码)

### 3.1 既有命令 → 静态库公共 API

| 命令 | 静态库 API | 现状行为 |
|------|-----------|----------|
| `asm assemble <code> [--hex] [--c-array]` | `asm_assemble(code, bytes, text)` | 内联汇编字符串 → 字节,支持 hex/c-array 输出;无文件输入,无 .bin 写出 |
| `shellcode inject <hex>` | `shellcode_inject(bytes, info)` | 分配(PAGE_EXECUTE_READWRITE)+ 写入 + **CreateRemoteThread 立即执行** + 记录持久化 |
| `shellcode injectat <addr> <hex>` | `shellcode_inject_at(addr, bytes, info)` | 指定地址写入 + 立即执行 + 记录持久化 |
| `shellcode status` | `shellcode_status(list)` | 列出注入记录(PID 级持久化,含 running 状态) |
| `dll inject/eject/list/status` | `dll_*` | DLL 注入/卸载(卸载先例:记录 → 远程线程调用 → 删记录) |
| `thread list/suspend/resume/kill` | `thread_*` | 线程枚举/挂起/恢复/结束;无「创建远程线程」命令 |
| `mem read/write/dump/regions/readval` | `memory_*` | 内存读写(注入后可用 mem 验证 shellcode 写入) |
| `disasm at/range` | `disasm_*` | 反汇编(注入后可验证机器码) |
| `convert <type> <value>` | 无(CLI 自实现,标准 C++ 位操作) | 类型化数据 → hex 字节文本;无文件写出 |

### 3.2 关键现状事实

1. **`shellcode inject` 已经是「分配+写入+立即执行」一体**:底层 `CreateRemoteThreadEx`
   在写完后立即创建远程线程执行,且 `InjectRecord` 持久化到
   `%TEMP%/deeptrace_<pid>/injects.dat`(跨 CLI 调用可见,`shellcode status` 可查)。
2. **不存在「只分配+写入、不执行」的动作**:用户设想的「分配 → 输出首地址」与
   「执行」分离,当前 API 无法表达。
3. **不存在「对已分配地址单独触发执行」**:无 `shellcode run <addr>`。
4. **不存在「释放已分配地址」**:无 `shellcode free <addr>`(dll 组有 eject 先例)。
5. **无文件输入**:asm 只吃内联字符串;shellcode 只吃 hex 字符串。
6. **无 hex → .bin 文件写出**:module dump 有「写文件」先例,但无 hex 字节写 .bin 命令。
7. 静态库基础设施已具备:内存层 `RemoteAlloc/RemoteFree/WriteRemoteMemory`,
   注入层 `CreateRemoteThreadEx/WaitRemoteThread/IsRemoteThreadRunning`(dll_inject 已用)。
8. CLI 硬约束:一次调用 = 一个操作;会话生命周期 = 本次 CLI 进程;输出纯 ASCII;
   `-p <pid>` 单次调用自动 attach/detach;**注入记录按 PID 持久化,可跨调用衔接**。

## 4. 现有流程正确性初步分析(供需求分析参考)

- 用户设想的「分阶段」流程**基本可行**,且与 CLI 无状态约束兼容:分配(alloc)→ 执行(run)
  → 复用/释放(free)各为独立命令,通过 `injects.dat` 记录跨调用衔接。
- **「复用远程线程触发」语义澄清**:已结束的线程无法复用,「复用」= 对同一已分配地址
  再次创建一条新远程线程触发一次(run 可重复执行)。
- **现有 `shellcode inject` 立即执行语义**与「分配与执行分离」冲突,需决策:
  保持兼容(inject 照旧,新增 alloc 不执行)或改造。
- **缺失能力集中在静态库**:需新增 `shellcode_alloc`(只分配+写入)、
  `shellcode_run`(触发一次)、`shellcode_free`(释放+清记录)三个公共 API,
  均可用既有基础设施实现 → 触发 `.flow/cpp_static_flow.md` 跨流程需求接收。
- **文件输入/写出属于 CLI 层能力**(标准 C++ 文件 I/O,符合「CLI 只用标准库」约束),
  不依赖静态库。
