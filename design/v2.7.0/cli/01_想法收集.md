# v2.7.0 想法收集:alloc near 真实就近分配(±2GB 内)

> 输入:用户问「把 alloc 的 near 第三参数改为真正就近分配(±2GB 内),消除 RIP
> 相对位移超界的概率」。

## 1. 现状调查(结论)

| 能力 | 现状 |
|---|---|
| `alloc(name,size)` 远程分配 + 符号记录 | ✅ 支持(script_alloc,OS 任意选址) |
| `alloc(name,size,"m.dll"+0x1234)` 第三参数语法解析 | ✅ 支持(CLI aa 解析器) |
| 第三参数模块加载校验(resolve_enable) | ✅ 支持(但解析出的锚点被丢弃) |
| **第三参数真实就近分配** | ❌ **不支持(v2.5.0 明确记录「放置提示,不保证就近」)** |

静态库 `RemoteAlloc` 是裸 `VirtualAllocEx(nullptr, size, ...)`——OS 完全任意
选址,可能与锚点(如 GameAssembly.dll+0x701B50)相差数 GB。此时脚本里生成的
RIP 相对跳转(如 `"m.dll"+0x7D5778: jmp newmem`)位移超过 ±2GB(disp32 上限),
运行时直接非法指令/访问违例。这正是用户要消除的概率。

CLI 侧 `resolve_enable` 已经解析了 near 表达式并校验模块加载,但解析结果
没有被传给分配调用(exec_enable 调 `script_alloc` 完全忽略 near)。

## 2. 用户诉求拆解

- `alloc(newmem, 2048, "GameAssembly.dll"+0x7D5778)` → 分配必须落在
  锚点 ±2GB 内(最好是贴近锚点),保证 `jmp newmem` 的 rel32 位移不超界。
- 距离越近越安全:同一页/同一 2GB 窗口内,rip-relative 引用越稳。

## 3. 方案要点

- **静态库基础设施 `RemoteAllocNear(hprocess, size, prot, anchor, &addr)`**:
  以 anchor 为中心,用 VirtualQueryEx 在 ±2GB 窗口内找空闲区(MEM_FREE),
  选择「距 anchor 最近且 size 可放下」的区,再取区内距 anchor 最近位置
  VirtualAllocEx 提交。窗口内无合适空闲区 → 返回错误。
- **静态库公共 API `script_alloc_near(name, size, anchor, &addr)`**:near
  版 script_alloc(分配 + 符号记录 + 落盘),错误语义与 script_alloc 对齐
  (AllocFault/InvalidArg),窗口无空闲 → AllocFault。
- **CLI**:resolve_enable 把 near 表达式解析出的锚点地址传给 exec_enable;
  exec_enable 有锚点则调 script_alloc_near,无则调 script_alloc(行为不变)。
- **错误暴露**:`script run` 时 near 就近失败报清晰错误(AllocFault),不静默
  退化为任意分配。

## 4. 边界与风险(记录)

- ±2GB 是 RIP 相对 disp32 硬上限;窗口内空闲区不足时分配失败是正确行为
  (宁可失败,不可远配)。
- 扫描成本:VirtualQueryEx 步进 MEM_FREE 区域(一般几十次调用),开销可忽略。
- 锚点表达式沿用 v2.5.0 语法(模块基址+偏移 / 裸地址),不做语法变更。
- 32 位进程无此问题(全地址空间 < 2GB),x64 下启用;窗口计算按 64 位地址。
